# Персональные данные: регламент эксплуатации форм

Это технический регламент для ООО «Интерно», а не заключение о полном соответствии 152-ФЗ. Оператор должен утвердить документы, выбранные основания и сроки, назначить ответственного и проверить договоры с провайдерами, локализацию, необходимость уведомления Роскомнадзора и организационные меры защиты. Публикация чекбокса не заменяет эти обязанности.

## Что фиксируется

- Документ: `/consent/2026-10-09-v1`, отдельный от политики `/policy`.
- Флажок изначально снят, нужен для одной заявки; рекламного согласия нет.
- Сервер принимает только `consent.accepted === true`, актуальную версию и известный вид формы после проверки CAPTCHA.
- Перед SMTP-отправкой подтверждение записывается с fsync в `/var/lib/interno-email/consents/UUID.json`.
- Состав записи: UUID, дата/время UTC, дата истечения, вид формы, версия, путь и SHA-256 документа. Нет имени, телефона, email, IP, CAPTCHA-токена или параметров товара.
- UUID и сведения о согласии включаются в письмо оператору, UUID также показывается пользователю после успешной отправки. Связь с субъектом определяется по исходному письму, а не по дополнительной базе контактов.
- Запись подтверждает получение согласия сервером, но сама по себе не подтверждает успешную доставку письма.

## Сроки

Для обычной заявки выбран технический срок 90 дней с момента отправки, либо до достижения цели/отзыва согласия при отсутствии других законных оснований. Оператор должен подтвердить этот срок для своего процесса.

1. **Серверные подтверждения:** ежедневный `interno-consent-prune.timer` удаляет записи с истёкшим `expiresAt`. Возможна задержка до ближайшего суточного запуска и 15 минут рандомизации. Незавершённые временные файлы старше суток удаляются тем же заданием. Повреждённая запись не уничтожается молча: задание сообщает агрегированную ошибку и требует проверки администратора.
2. **Новые журналы Express:** отдельный namespace `interno-email`, MaxRetentionSec=14day, ротация раз в сутки, лимит 32 MiB. Содержат только технические коды ошибок и служебные сообщения. Старые записи в общем journald не были выборочно удалены: их безопасное удаление затрагивает другие службы и требует отдельной согласованной операции.
3. **Nginx:** существующая ежедневная ротация с 14 архивами. В HTTP-журналах возможны IP, время, URL и User-Agent; формы передают данные в теле POST, не в URL. Не добавлять логирование тела, email, телефона или CAPTCHA-токенов.
4. **Письма и рабочие материалы:** удаляются оператором отдельно. Серверное задание НЕ управляет почтой Яндекса, CRM, файлами сотрудников или пересылками.
5. **Договоры/бухгалтерия:** при заключении договора определить самостоятельные основания и обязательные сроки. Не переносить общий срок заявки на документы, которые нужно хранить по закону.
6. **Резервные копии:** проверить фактическое расписание и число копий в Timeweb. Ограничить доступ, определить срок удаления дополнительных ручных копий, учитывать обращения об удалении при восстановлении. Ручные копии исходников и `.env` должны оставаться вне веб-каталога с доступом только root; не включать в Git.

## Плановая очистка почты — обязанность оператора

Назначенный сотрудник еженедельно проверяет служебный ящик и связанные рабочие материалы, включая заявки, срок которых истекает в следующие семь дней. Дату удаления нужно назначать не позднее установленного срока, а при достижении цели или отзыве — с учётом более раннего применимого срока:

- найти обычные заявки, достигшие цели или приближающиеся к предельному сроку хранения;
- проверить, не появились ли договорные/законные основания дальнейшего хранения;
- удалить не требующие дальнейшей обработки письма, вложения, копии, пересылки и экспортированные файлы;
- удалить их из корзины в пределах применимого срока, учесть особенности резервных копий провайдера;
- зафиксировать дату, исполнителя, объём и основание очистки без избыточных контактных данных.

Автоматическую IMAP-очистку без классификации писем не включать: она может уничтожить действующие заказы, договорные материалы или обращения об удалении. SMTP-доступ не даёт подтверждённого разрешения читать и удалять содержимое ящика.

## Обращение об удалении / отзыв согласия

Канал: `mebelme8@yandex.ru` или почтовый адрес из опубликованной политики. Нельзя требовать отправку формы заказа или новой CAPTCHA для такого обращения.

1. Зарегистрировать дату получения, канал, требование, минимально необходимые сведения для поиска заявки и ответственного. Не запрашивать паспорт автоматически.
2. Проверить личность в необходимом объёме, найти письмо по контакту/дате/UUID и уточнить применимые основания. Если часть данных нужно сохранить по закону, обосновать это и ограничить использование этой части.
3. Остановить обработку, основанную на отозванном согласии, и исполнить обращение в сроки закона. По общему правилу уничтожение после отзыва без других оснований — не более 30 дней. Другие виды запросов имеют собственные сроки; ответственный должен проверить их.
4. Удалить письмо и копии в почте/рабочих системах; поручить нужные действия привлечённым лицам. Удалить серверное подтверждение при отсутствии основания его дальнейшего хранения:

   ```sh
   # Сначала проверка: удаление не выполняется без --execute.
   sudo -u interno-mail node /var/www/email-service/scripts/consents-admin.cjs delete --id UUID
   sudo -u interno-mail node /var/www/email-service/scripts/consents-admin.cjs delete --id UUID --execute
   ```

5. Зафиксировать исполнение и ответить субъекту. Не считать удаление одного JSON-файла удалением заявки из почтового ящика.
6. Сохранить минимальный реестр исполненных требований в утверждённом оператором месте. Перед восстановлением из резервной копии сверить его и повторно удалить ранее удалённые записи/письма до возврата системы в работу.

## Контроль администратора

```sh
systemctl status email-service.service
systemctl list-timers interno-consent-prune.timer
systemctl show interno-consent-prune.service -p Result -p ExecMainStatus
# Содержимое журналов может быть конфиденциальным — не публиковать.
journalctl --namespace=interno-email -u email-service.service
# Без удаления, только агрегированные счётчики:
sudo -u interno-mail node /var/www/email-service/scripts/consents-admin.cjs prune
```

`CONSENT_REQUIRED=true` должен оставаться включённым. Временная совместимость допускается только при координированном релизе: нужны одновременно `CONSENT_REQUIRED=false` и явный будущий `CONSENT_LEGACY_UNTIL`. После срока режим автоматически перестаёт принимать заявки без согласия; после публикации сайта временный override удаляется. Старые заявки не получают выдуманного подтверждения согласия.
